لماذا نستخدم signal في الترتيب؟

اليوم تعطي النسختان نفس النتيجة، وفرق الأداء أقل من 0.3 ms لكل عملية. الفرق الحقيقي يظهر في التغييرات القادمة: ثلاث ميزات متوقعة تحتاج signal على أي حال، وميزتان تعملان في النسخة العادية فقط إذا تذكّر المطوّر قاعدة. التوصية: نُبقي الـ signal.

01الفكرة

التصميمان باختصار

نسخة الـ signal تعامل الترتيب كـ قيمة مشتقة: القائمة المعروضة تُحسب من البيانات ومن حالة الترتيب، وتُعاد تلقائياً إذا تغيّر أيٌّ منهما. النسخة العادية تعامل الترتيب كـ حدث: نرتب في لحظات نختارها، ونحفظ النتيجة مرتبة فوق البيانات نفسها.

contacts.store.tsنسخة الـ signal (الحالية، مختصرة)
// الحالة: كل مفتاح في withState يصبح signal
sortState: { column: '', direction: 'asc' },

// القائمة المعروضة: تُحسب من البيانات + حالة الترتيب
sortedContacts: computed(() => sortContacts(contacts(), sortState())),

sortBy(column) {
  patchState(store, { sortState: { column, direction } });
}
contacts.store.tsالنسخة العادية (بدون signal)
let sort = { column: '', direction: 'asc' };   // متغير عادي

function setFirstPage(contacts) {
  patchState(store, { contacts: sortContacts(contacts, sort) });   // نرتب عند الكتابة
}

// داخل loadMore
contacts: sortContacts([...contacts, ...newData], sort),

sortBy(column) {
  sort = { column, direction };
  patchState(store, ({ contacts }) => ({ contacts: sortContacts(contacts, sort) }));
}

currentSort() { return sort; }   // للأسهم في عناوين الأعمدة
القاعدتان اللتان تفرضهما النسخة العادية

النسخة العادية تمر في الـ Angular compiler بدون أخطاء وتعمل اليوم، لكنها تفرض على كل كود يُكتب لاحقاً:

  1. القاعدة ①: كل كتابة في contacts يجب أن تمر عبر sortContacts.
  2. القاعدة ②: كل تغيير في sort يجب أن يتبعه patchState على contacts، وإلا لا تتحدث الشاشة.

03اليوم

نفس السلوك، وفرق أداء لا يُرى

كل ما تفعله ميزة الترتيب اليوم يعمل بنفس الشكل في النسختين، لذلك لا يمكن الحكم بينهما من الشاشة الحالية.

الأداء، مقاساً على جهاز التطوير بـ Node (محرك V8، نفس محرك Chrome و Edge):

القياسsignalعادية
قراءة قيمة الترتيب مرة واحدة5.3 ns3.1 ns
جلسة كاملة: 5 ضغطات + 20 loadMore + 5 حذف (من 100 إلى 300 صف)3.82 ms (30 ترتيباً)0.89 ms (25 ترتيباً)

فرق الجلسة كلها أقل من 3 ms، بينما يرسم المتصفح إطاراً كل 16.7 ms. وسبب سرعة النسخة العادية ليس غياب الـ signal: هي تحفظ القائمة مرتبة، وترتيب قائمة شبه مرتبة أسرع. هذه الفكرة نفسها يمكن تطبيقها مع إبقاء الـ signal.

عند 10,000 صف يصبح الفرق ملحوظاً (حتى 21 ms لكل loadMore في نسخة الـ signal)، لكن الترتيب في المتصفح عند هذا الحجم خاطئ أصلاً: هو يرتب المحمّل فقط. الحل هناك هو الترتيب على السيرفر (الميزة 3).

04التغييرات القادمة · 1

ثلاث ميزات تحتاج إعادة تصميم في النسخة العادية

هذه الميزات لا يحلها التذكّر: النسخة العادية تحتاج تغيير تصميمها نفسه، أو تعود إلى signal. المخرجات من تشغيل حقيقي، ببيانات سيرفر ترتيبها: Nablus, Amman, Jenin, Hebron (الميزة 3 تضيف Ramallah و Gaza).

الميزة 1: إلغاء الترتيب (الرجوع لترتيب السيرفر)

النسخة العادية لا تستطيع الرجوع حتى مع تطبيق القاعدتين، لأن ترتيب السيرفر ضاع لحظة كتبنا القائمة المرتبة فوق contacts.

✓ signal
clearSortسطر واحد
clearSort() {
  patchState(store, { sortState: { column: '', direction: 'asc' } });
}
✗ عادية
clearSortتطبّق القاعدتين معاً، ولا يكفي
clearSort() {
  sort = { column: '', direction: 'asc' };
  patchState(store, ({ contacts }) => ({ contacts: sortContacts(contacts, sort) }));
}
المخرجات الحقيقية

لإصلاحها تحتاج النسخة العادية طلباً جديداً من السيرفر، أو قائمة ثانية serverOrder تُحدّث مع كل loadMore وحذف وتعديل، أي قواعد إضافية.

الميزة 2: حفظ الترتيب المفضّل (أو وضعه في الـ URL، أو analytics)

في نسخة الـ signal يلتقط سطر واحد كل تغيير في الترتيب من أي مكان. في النسخة العادية لا يوجد ما يمكن مراقبته.

✓ signal
effectيعمل مع كل تغيير
effect(() => savePreference(store.sortState()));
✗ عادية
effectنفس السطر، لكن لا شيء يُراقَب
effect(() => savePreference(store.currentSort()));

في النسخة العادية يجب استدعاء savePreference() يدوياً داخل sortBy و clearSort و restoreSort، وداخل كل دالة قادمة تغيّر الترتيب.

الميزة 3: الترتيب على السيرفر

هذا هو الحل الصحيح لمشكلة موجودة اليوم: الترتيب يشمل الـ contacts المحمّلة فقط، والسيرفر يرسل الصفحات بترتيب id.

✓ signal
queryسطر واحد، والـ switchMap يُلغي القديم
query: computed(() => ({ term: searchTerm(), letter: selectedLetter(), sort: sortState() })),
✗ عادية
sortByالمتغير لا يدخل computed، فيطلب وحده
sortBy(column) { sort = { column, direction }; reloadFirstPage(); }

السيناريو: نكتب "a" فيبدأ طلب بحث بطيء (A، 300 ms)، ثم نضغط City فوراً فيبدأ طلب سريع (B، 100 ms).

05التغييرات القادمة · 2

ميزتان تعملان في النسخة العادية فقط إذا تذكّر المطوّر قاعدة

في نسخة الـ signal، الكود الطبيعي لهاتين الميزتين صحيح. في النسخة العادية، الكود الطبيعي خطأ لا يُظهر أي error، والصحيح يحتاج تذكّر قاعدة.

الميزة 4: تعديل contact، أو Realtime يرسل تحديثاً (القاعدة ①)

نفس الكود الطبيعي في النسختين:

updateContactنفس الكود في النسختين
patchState(store, ({ contacts }) => ({
  contacts: contacts.map((c) => (c.id === '2' ? { ...c, city: 'Zarqa' } : c)),
}));

القائمة مرتبة حسب City ↑، وغيّرنا Amman إلى Zarqa:

في النسخة العادية تظهر Zarqa أول القائمة تحت سهم City ↑. الإصلاح لفّ القائمة بـ sortContacts(...)، أي تذكّر القاعدة ① في كل مكان يكتب في contacts.

الميزة 5: الترتيب المحفوظ يصل من السيرفر بعد await (القاعدة ②)

✓ signal

✗ عادية
restoreSortنسيت القاعدة ②
restoreSort(saved) { sort = saved; }

  • بعد الضغط على زر لا علاقة له بالترتيب، يتغير السهم إلى ↓ وتبقى الصفوف تصاعدية: الشاشة تناقض نفسها.
  • السطر الأخير: مع patchState تعمل النسخة العادية بشكل صحيح.
لماذا لا تتحدث الشاشة؟

التطبيق zoneless، فالشاشة تتحدث فقط عندما يتغير signal أو بعد حدث في الـ template. تغيير متغير عادي بعد await لا يُبلّغ أحداً.

06بإنصاف

أين النسخة العادية أفضل

للنسخة العادية ثلاث مزايا حقيقية، والأولى قرار منتج وليست قراراً تقنياً.

  1. صورة ثابتة مقابل ترتيب حي. في الميزة 4 انتقل الصف المعدّل في نسخة الـ signal من أول القائمة إلى آخرها. إذا كان المستخدم يعدّل داخل الجدول، يختفي الصف من تحت يده. إذا كان المطلوب أن يكون الترتيب أمراً لمرة واحدة (مثل Sort في Google Sheets)، فسلوك النسخة العادية هو الصحيح. وإذا كان المطلوب أن تبقى القائمة مرتبة دائماً، فنسخة الـ signal هي الصحيحة.
  2. وضوح لحظة التنفيذ. الـ breakpoint داخل sortBy يُظهر متى يحدث الترتيب بالضبط. أما الـ computed فيعمل عند القراءة أثناء رسم الشاشة، والـ stack trace يمر عبر Angular. هذا أسهل على من لا يعرف الـ signals.
  3. الأداء. أسرع بأقل من 3 ms في جلسة كاملة (القسم 03)، وهو فرق لا يلاحظه المستخدم.

08التوصية

القرار

نُبقي الـ signal

القائمة تُحمّل من Supabase على صفحات، والحل الصحيح للترتيب على المدى الطويل هو السيرفر (الميزة 3)، وهو يحتاج signal على أي حال.

النسخة العادية اختيار سليم فقط إذا تحققت الشروط الثلاثة معاً:

  • المنتج يريد الترتيب "صورة ثابتة"، وليس ترتيباً حياً.
  • لا توجد خطة لإلغاء الترتيب أو حفظه أو نقله إلى السيرفر (الميزات 1 إلى 3).
  • تُكتب القاعدتان ① و ② في تعليق فوق let sort، ويُراجَع على أساسهما كل كود جديد يكتب في contacts أو يغيّر الترتيب.
سؤال مفتوح للفريق

هل نريد ترتيباً حياً (الصف ينتقل فور تعديله) أم صورة ثابتة (يبقى مكانه حتى الترتيب التالي)؟

الخلاصة في جملة

اليوم النسختان متساويتان في النتيجة والأداء، لكن إلغاء الترتيب وحفظه ونقله إلى السيرفر تحتاج signal في كل الأحوال.

09الدليل

كيف تحققنا

كل المخرجات في هذه الصفحة من تشغيل حقيقي على نسخة تجريبية من المشروع، ولم يُعدّل المشروع نفسه.

  • الإصدارات: Angular 22.2.1، و @ngrx/signals 22.0.1، و RxJS 7.8.2، و Vitest 5.0.3، و TypeScript 6.0.3.
  • النسختان: ملف الـ store الحالي، ونسخة بدون signal بنفس دالة المقارنة. النسخة العادية تمر في الـ Angular compiler بدون أخطاء، مع ملف تحكم فيه خطأ متعمد للتأكد أن فحص الـ templates يعمل.
  • الميزات 1 و 2 و 4 و 5: 8 اختبارات بـ ng test (Vitest، و zoneless مثل التطبيق)، نجحت كلها. الـ services استُبدلت بـ 4 contacts وهمية.
  • الميزة 3: محاكاة بـ RxJS من المشروع، مع تأخير وهمي للطلبات (A: 300 ms، B: 100 ms).
  • الأداء: Node على جهاز التطوير، مليون قراءة لكل نوع، والوسيط من 21 إلى 31 تشغيلاً لكل ترتيب. الأرقام تختلف من جهاز لآخر، لكن النسب بينها تبقى متقاربة.
